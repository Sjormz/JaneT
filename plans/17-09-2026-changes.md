# JaneT release-process changes

Date: 17 September 2026

## Goal

Shorten the path from an approved change to a published JaneT release without weakening review, CI, CodeQL, packaging, or exact-SHA safeguards.

## Agreed changes

### 1. Parallelize release verification and packaging

Keep a small `prepare` job responsible for validating the tag, version, and source SHA. After that job passes, run the full verification job and the Linux/macOS/Windows packaging jobs in parallel.

Current critical path:

```text
prepare -> full verification -> platform packaging -> publish
```

Target critical path:

```text
                 +-> full verification -+
prepare ---------+                       +-> publish
                 +-> platform packaging-+
```

This preserves every gate while removing the unnecessary wait for packaging to begin. The v0.11.4 release took about 10 minutes 24 seconds; this should reduce the workflow critical path to roughly 5-6 minutes, subject to runner and packaging time.

### 2. Defer new Codex-specific test work

Do not add a fake Codex executable, a real-Codex integration lane, or specialized Codex environment setup as part of this process improvement.

The existing shipped regression coverage remains unchanged. Revisit deterministic "Codex present/absent" fixtures and an optional real-Codex integration lane as a separate future change.

### 3. Use a PR label as explicit release intent

Add a plain `release` label directly to the release PR. No special release branch is required just to opt into the automated handoff.

The automated handoff runs only when all of the following are true:

- the PR was merged, not merely closed;
- the merged PR had the `release` label;
- the merge changed the application version;
- `package.json`, `package-lock.json`, and the lockfile root version agree;
- the new version is greater than the latest published release;
- required CI and CodeQL checks are green for the exact merge SHA;
- the tag and GitHub Release do not already exist.

When those checks pass, automation creates the annotated tag for the exact merge commit and starts the existing release workflow. Ordinary merged PRs without the label or a version change do nothing.

The automation must continue to fail closed: no force-pushes, tag moves, release overwrites, review bypasses, or publishing from an unverified commit.

## Explicitly dropped

- Do not optimize or cache `npm ci` as part of this work. It was not the primary v0.11.4 bottleneck and could add native-module cache risk.

## Expected result

The process becomes faster through parallel execution and less manual handoff, while keeping the existing reviewed-PR, protected-main, exact-SHA, cross-platform packaging, and public-release verification model intact.
